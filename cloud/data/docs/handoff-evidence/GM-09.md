## 6. R01 审查重构与 Runner 集成接口规范 (R01 Rework & Runner Interface Specification)

### 6.1 审查诊断与根因 (R01 Review Diagnosis)
Codex 审查指出：
1. 默认情况下，调度运行环境使用 `createConnector()` 且未持久化传入 `previousObservations`；若两次运行在不同连接器实例间执行，缺乏对跨运行历史记录的感知；
2. 原先对 `sourceUpdatedAt` 的校验仅检查 `sourceUpdatedAt === null`，一旦上游返回非空 `Last-Modified`，未能保证新旧修订时间戳之间的严格单调递增性（相同时间戳或迟到的旧版本时间戳未被阻止）。

### 6.2 持久化检查点与摘要接口定义 (Checkpoint & Summary Interface)
在 `cloud/data/src/connectors/com_pedestrian_hourly/index.ts` 中导出如下规范接口：
```typescript
export interface HourlyRecordSummary {
  recordId: string;
  sensorHourKey: string;
  versionId: string;
  sourceUpdatedAt: string | null;
  count: number | null;
}

export interface HourlyCheckpoint {
  cursor: string;
  summaries: HourlyRecordSummary[];
}

export function parseHourlyCheckpoint(checkpoint: string | null): HourlyCheckpoint | null;
```

### 6.3 严格单调修订判定矩阵 (Monotonic Revision Matrix)
当检测到同一传感器小时实体 `(sensor_id, observed_at)` 出现不同 `version_id` 时，执行以下判定：

| 上游与历史时间戳状态 | 判定行为 | 返回错误代码与消息 |
| :--- | :--- | :--- |
| `T_new === null \|\| T_old === null` | 严格失败关闭 | `validation_failed: Conflicting duplicate sensor-hour readings across versions without revision order` |
| `T_new` 或 `T_old` 无法解析为有效时间戳 | 严格失败关闭 | `validation_failed: Conflicting duplicate sensor-hour readings across versions without valid revision timestamp` |
| `tNewMs === tOldMs`（时间戳相同，无序） | 严格失败关闭 | `validation_failed: Conflicting duplicate sensor-hour readings with identical revision timestamp` |
| `tNewMs < tOldMs`（较旧版本迟到） | 严格失败关闭 | `validation_failed: Conflicting duplicate sensor-hour readings with older revision timestamp arriving late` |
| `tNewMs > tOldMs`（严格单调递增更新） | 允许推进更正 | 成功，生成更新的 `sourceRevision` 与 `stableBatchId`，更新历史摘要 |
| `version_id` 完全相同（内容无变动重放） | 幂等通过 | 成功，输出记录与既有版本保持一致 |

### 6.4 Runner 调度器集成要求 (Runner Integration Guidelines)
- **当前现状**: `ingest.ts` 将 `input.checkpoint` 传递给连接器，但 `publisher.ts:markPublishedWindow` 默认写入时间戳字符串（如 `2024-10-30`）。
- **进程内支持**: 连接器实例在单个进程常驻生命周期内已内建 `knownSummariesBySensorHour`，同一实例连续调用可自动阻断无序更正。
- **跨进程持久化对接要求**: 生产 Runner 需将连接器返回的 `result.checkpointAfter`（包含 `{ cursor, summaries }` 的 JSON 格式）持久化至状态存储，并在下次触发 `collect()` 时作为 `input.checkpoint` 传入。连接器内的 `parseHourlyCheckpoint` 已向后兼容纯字符串游标、旧式 `previousObservations` 对象数组及新式 `HourlyCheckpoint`。
- **准入声明**: 在 Runner 完成跨运行 Checkpoint 状态存储闭环前，本连接器保持 `access_status = candidate`，不可提前准入生产环境。
