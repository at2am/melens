## 3. 真实调用断言与隔离验证说明

### 3.1 真实生产函数调用链路 (Real Production Function Invocations)
测试直接导入并执行核心生产实现：
- `computeSourceHealth`（`cloud/data/src/core/health.ts`）
- `computeCoverageStatus`（`cloud/data/src/core/health.ts`）
- `addCompletedWindow`（`cloud/data/src/core/gcs.ts`）
- `BigQueryPublisher.publish`（`cloud/data/src/core/publisher.ts`）
- `BigQueryPublisher.recordConnectorFailure`（`cloud/data/src/core/publisher.ts`）
- `BigQueryPublisher.pauseSource`（`cloud/data/src/core/publisher.ts`）

### 3.2 真实函数变坏敏感性：恢复演进与间隙断言 (Recovery & Gap Sensitivity)
- **乱序到达与间隙拦截**：
  - 初始 Checkpoint 为 `00:00:00Z`，窗口 1（`00:00 ~ 01:00`）成功后 Checkpoint 推进至 `01:00:00Z`。
  - 窗口 2（`01:00 ~ 02:00`）发生故障缺失，窗口 3（`02:00 ~ 03:00`）乱序到达。
  - 执行生产 `addCompletedWindow`：断言 Checkpoint **严格停留在 `01:00:00Z`**，绝不越过缺失的窗口 2；窗口 3 存入 `completedWindows` 队列。
- **间隙存在时的健康度与覆盖度拦截**：
  - 调用生产 `computeSourceHealth({ knownGapCount: 1, latestCheckSucceeded: true, ... })`：
    - 状态必须为 `'unknown'`，`reason` 必须匹配 `/coverage gap is known/`。
  - 调用生产 `computeCoverageStatus({ matchingRecords: 0, completeWindow: true, ... })`：
    - 即使查询出 0 条记录，覆盖度状态必须为 `'unknown'`，**绝不能返回 `'no_matching_records'`**。
- **间隙补齐与 Checkpoint 跃进**：
  - 重放缺失的窗口 2（`01:00 ~ 02:00`）送入生产 `addCompletedWindow`。
  - 断言 Checkpoint **直接跃进至 `03:00:00Z`**，`completedWindows` 清空。
  - `computeSourceHealth({ knownGapCount: 0, consecutiveFailures: 0, latestCheckSucceeded: true })` 状态恢复为 `'current'`。
  - `computeCoverageStatus` 此时方允许对 0 匹配记录认证为 `'no_matching_records'`，对 >0 匹配记录认证为 `'covered'`。
- **变坏敏感性**：如果 `addCompletedWindow` 逻辑退化（如错误地忽略间隙直接推进至 03:00，或在闭合间隙后丢失窗口 3 未能推进至 03:00），或者 `computeSourceHealth` 在存在间隙时错误返回 `current`，该用例将立即失败。

### 3.3 真实函数变坏敏感性：失败批次隔离验证 (Failed Batch Isolation)
- **连接器失败上报隔离**：
  - 调用真实 `publisher.recordConnectorFailure(source, failure, windowFrom, windowTo)`。
  - 断言生产 `SyncBatch` 状态：
    - `state = 'failed'`
    - `error_code = 'upstream_unavailable'`
    - `published_at = null`
    - `checkpoint_after = null`
  - 断言存储与元数据隔离：
    - GCS Manifest 中的 `checkpoint` 严格维持在上次成功时间，**绝不前进**。
    - `data_sources` 中的 `last_success_at` 严格维持原值，**绝不篡改**。
    - `last_checked_at` 更新为失败检查时刻。
- **发布校验拒绝与批次隔离**：
  - 构造包含非法数据（如负数序号 `source_version_ordinal = -1`）的真实 `ConnectorSuccess` 载荷送入 `publisher.publish()`。
  - 断言 `publisher.publish()` 抛出校验异常被拒绝。
  - 断言内部事务流转：捕获异常后将批次标记为 `state = 'failed'`, `error_code = 'validation_failed'`，Checkpoint 严格不变。
- **覆盖度隔离**：
  - 无论在失败窗口内通过何种方式查询出 0 条记录，传入 `computeCoverageStatus` 均只能得出 `'unknown'`，彻底杜绝失败批次被当作“无事件发生”。
- **变坏敏感性**：如果发布器在失败时错误地更新了 `last_success_at` 或推进了 Checkpoint，断言将立即失败阻断。

### 3.4 空结果真实语义约束 (Empty-Result Meaning Strict Constraints)
通过组合矩阵对生产 `computeCoverageStatus` 进行全面单测约束，证明 **“0 条记录”绝对不等于“无事件发生”**：
1. **覆盖源为空** (`coveringSources = []`)：返回 `'not_covered'`（非 no_matching_records）。
2. **窗口不完整** (`completeWindow = false`)：返回 `'unknown'`（非 no_matching_records）。
3. **覆盖源存在延迟** (`state = 'late'`)：返回 `'unknown'`（非 no_matching_records）。
4. **覆盖源过期失效** (`state = 'stale'`)：返回 `'source_unavailable'`（非 no_matching_records）。
5. **覆盖源存在间隙** (`knownGapCount > 0`)：返回 `'unknown'`（非 no_matching_records）。
6. **覆盖源存在连续失败** (`consecutiveFailures > 0`)：返回 `'unknown'`（非 no_matching_records）。
7. **多源覆盖中有一源延迟** (`current + late`)：返回 `'unknown'`（非 no_matching_records）。
8. **多源覆盖中有一源过期** (`current + stale`)：返回 `'unknown'`（非 no_matching_records）。
9. **多源覆盖全部过期** (`stale + stale`)：返回 `'source_unavailable'`。
10. **非法数值输入保护** (`matchingRecords < 0` 或小数)：抛出 `Error('Invalid matching record count')`。
11. **全部 5 项严格条件同时满足**（全源 current、无间隙、无失败、窗口完整、且有合法覆盖源）：此时 0 条记录才被认证为 `'no_matching_records'`。

### 3.5 来源撤销与至少一次幂等性 (Revocation & Idempotence)
- **`publisher.pauseSource`**：
  - 验证物理事实删除、存储副本清除、元数据变更为 `access_status: 'paused'` 与 `license_status: 'review_required'`。
  - 验证暂停后的源健康度为 `unknown`，下游覆盖度降级为 `unknown`。
- **至少一次重试幂等性**：
  - 重复发布同一成功窗口，验证返回原 `SyncBatch`，Checkpoint 不变，BigQuery 物理表行数不发生翻倍重复加载。

## 5. 接口与共享契约建议（供公共模块维护者参考）

1. **`computeCoverageStatus` 的部分恢复状态表达**：
   - 当前当 `consecutiveFailures > 0` 且 `lastSuccessAt !== null` 时，若 `state === 'current'`（例如失败后紧接着成功），如果调用方未将 `consecutiveFailures` 重置为 0，`computeCoverageStatus` 仍会判定为 `unknown`。
   - **建议**：在调度框架或发布链路成功入库后，应由调度状态机统一重置该数据源的 `consecutiveFailures` 为 0，确保成功恢复的批次能够无缝反映在覆盖度查询中。
2. **`recordConnectorFailure` 的错误码分级**：
   - 当前失败记录支持 `rate_limited`, `upstream_unavailable`, `schema_changed`, `auth_failed`, `incomplete_window`, `validation_failed`。
   - 建议在未来版本中对 `rate_limited` 引入建议等待时间（`retryAfterSeconds`）的结构化存储，便于上层调度器执行退避重试而无需解析字符串日志。
