### 3.2 历史观测保真与现行设备状态严格区分

1. **废弃历史点位表排查 (`microclimate-sensor-locations`)**:
   - 官方 portal 曾包含旧版测试数据集 `microclimate-sensor-locations`（关联 56 条旧读数，2022 年后不再维护更新）。
   - 若系统使用该废弃表或全量 12 台历史设备作为静态资产清单，会将 6 台已停用设备（包括停用 3 个月的 `ICTMicroclimate-01`）错误标定为当前运行监测站。
2. **连接器行为原则 (`no_historical_inventory_rule`)**:
   - 区分两类业务需求：
     - **事实追溯需求（Historical Observations）**：即使是 3 个月前 `ICTMicroclimate-01` 的读数，也是发生过的不可变物理观测事实，必须完整保留在 `sourceRecords`、`geoRecords` 和 `areaIndicators` 中；
     - **现行点位查询需求（Current Equipment Inventory）**：历史观测**绝不能**输出 `device_status = 'active', valid_to = null`。连接器在单次批次中根据观测时效性，将陈旧读数的 `valid_to` 闭合在观测采样窗口末端（`observed_at + 15min`），并标定 `device_status = 'inactive'`。只有在当前窗口内活跃上报的设备，才具备未闭合的 `valid_to = null` 与 `device_status = 'active'`。

### 3.3 平台共享状态／视图能力接口建议 (Architecture & Interface Proposal)

> [!IMPORTANT]
> **关于跨批次设备生命周期视图的接口建议**:
> 单次连接器调用在架构上属于无状态提取器（Stateless Collector），每次仅拉取输入窗口内的遥测切片。连接器内部的 24 小时阈值仅能保障单批次内的时效判定，无法单独解决跨批次、跨天数运行中的传感器退役、维护断流或恢复上报等全生命周期设备状态管理。
>
> **接口与视图规范建议**：
> 建议在通用发布层（BigQuery / PostgreSQL）建立物化视图（Materialized View）或持续聚合任务，例如 `v_current_microclimate_devices`：
> ```sql
> CREATE OR REPLACE VIEW v_current_microclimate_devices AS
> WITH latest_readings AS (
>   SELECT
>     sensor_id,
>     MAX(observed_at) AS latest_observed_at
>   FROM `melens.sensor_locations`
>   WHERE source_id = 'melbourne.microclimate'
>   GROUP BY sensor_id
> )
> SELECT
>   s.sensor_id,
>   s.version_id,
>   s.geometry_geojson,
>   CASE
>     WHEN s.valid_from >= TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 1 HOUR) THEN 'active'
>     ELSE 'inactive'
>   END AS effective_device_status,
>   s.valid_from,
>   CASE
>     WHEN s.valid_from >= TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 1 HOUR) THEN NULL
>     ELSE TIMESTAMP_ADD(s.valid_from, INTERVAL 15 MINUTE)
>   END AS effective_valid_to,
>   s.source_record_id
> FROM `melens.sensor_locations` s
> INNER JOIN latest_readings l
>   ON s.sensor_id = l.sensor_id AND s.valid_from = l.latest_observed_at;
> ```
> 此机制彻底将**观测事实入库**（只增不改、历史事实永久有效）与**现行设备清单呈现**（滚动时间窗口计算活跃态）解耦。

## 5. 缺测保留与零值防混淆验证 (No-Zero-Filling)

1. **官方缺测实际存在证据**:
   - 官方数据集元数据 Known Issues 明确指出：“Note this dataset may not contain a reading every 15 minutes as the sensor devices might not have a reading for each value. There may be some situations where no readings are reported.”
   - 现场核查活跃设备 `aws5-0999`（Royal Park）：该气象站未搭载激光散射颗粒物与声级计传感器，官方接口上报的原始数据中 `pm25: null`, `pm10: null`, `noise: null`。
2. **缺测补零的严重危害**:
   - 若将 `pm25: null` 填零为 `0.0`，下游将误判该区域空气极其洁净（0 µg/m³）；
   - 若将 `noise: null` 填零为 `0.0`，下游将误判该公园完全无声（0 dB，低于人类听阈）。
3. **真实 0.0 与缺测 null 并存证据**:
   - 在真实遥测中，`minimumwindspeed: 0.0`（静风）与 `minimumwinddirection: 0.0`（正北风）为有效观测物理量。
4. **连接器行为保真约束**:
   - `toMetric()` 严格判定：当原始值为 `null`、`undefined` 或 `NaN` 时，输出 `{ value: null, unit, status: 'missing' }`，生成 `AreaIndicator` 时 `value: null, status: 'missing'`；
   - 真实 `0.0` 正常输出 `{ value: 0, unit, status: 'observed' }`，形成严格区分。

## 6. HTTP 边界生产分页与异常处理机制验证

1. **OpenDataSoft API v2.1 分页机制**:
   - 接口支持基于 `limit`（最大 100）和 `offset` 的标准分页，并在每个响应中附带 `total_count`。
2. **HTTP 边界分页机制实测与测试覆盖**:
   - **生产请求参数核验**：使用 `MockPaginationHttpClient` 在 HTTP 边界截获请求，验证 `OpenDataSoftClient` 真实发出了 `offset=0, limit=5; offset=5, limit=5; offset=10, limit=1` 请求序列，累计拉取 11 条记录并产出 3 页完整度指标；
   - **末页缺失/截断异常覆盖 (Truncated/Empty Page)**：上游声称 `total_count = 11` 但在后续页提前返回空数组 `[]` 时，触发 `OdsIncompleteWindow` 并映射为 `code: 'incomplete_window'` 优雅阻断；
   - **分页中总数漂移检测 (Total Count Drift)**：分页过程中上游新增数据导致 `total_count` 由 11 漂移至 12 时，严格阻断并报错 `'total_count changed during pagination'`；
   - **页间重复记录防混淆 (Cross-page Duplicates)**：
     - 若跨页边界出现完全相同的重复行，连接器安全去重，不膨胀记录数；
     - 若跨页边界出现同键冲突行（相同设备与时间但不同量测值），连接器立即 fail-closed 并抛出 `validation_failed: Conflicting duplicate reading`。
