| 标准要求 | 落实情况 |

| **1. Protobuf 字段与 ID 核对** | 校验 protobuf `FeedEntity.id`、路线（`routeId`/`directionId`）、站点（`stopId`）、车次（`tripId`）、生效区间（`activePeriods`/`communicationPeriods`/`impactPeriods`）；单一 impact period 正确派生 `valid_from`/`valid_to`，多区间或零区间置 `null` 保持事实完整性。 |

## 5. 2026-10-01 Follow-up 详细机制说明

### 5.1 不可变行防冲突机制 (Problem 1)
- **旧实现缺陷**：原先 `sourceVersionId(null, alert)` 只基于 alert 单体内容计算。当同一个 alert 在后续 feed 中持续发布但 `feedTimestamp` 推进时，其 `SourceRecord.source_updated_at` 与 `GeoRecord.summary.feed_timestamp` 变动，但 `version_id` 却保持相同。这导致 publisher 在入库校验时检测到同一 `row_key` 存在多种不同不可变内容，触发 `conflicts > 0` 报错。
- **新实现保障**：采用 `sourceVersionId(update, { mode: feed.mode, feedVersion: feed.parsed.feedVersion, alert })`。当上游快照时间戳 `update` 推进时，`version_id` 随之推进，旧记录保持历史不可变，新记录写入新版本。而在相同 `update` 下重放时，因 `fetchedAt` 属于审计字段而不纳入内容标识，重放生成的 `version_id` 与数据内容严格幂等一致，不产生多余逻辑版本。

### 5.2 双模式综合 Revision 机制 (Problem 2)
- **旧实现缺陷**：原实现取两模式时间戳的 `Math.max`。如果 Metro Train 为 `00:10:00`，Yarra Trams 为 `00:05:00`，最大值为 `00:10:00`。当下一次抓取中 Yarra Trams 推进至 `00:08:00`（依然小于 `00:10:00`）时，`sourceRevision` 依然返回 `00:10:00`，下游无法感知电车模式的内容更新。
- **新实现保障**：`deriveAlertFeedsRevision` 将双模式的模式名称、时间戳、publisher 版本与警报列表按规范排序后序列化并做哈希。任一模式（不论超前或落后）推进时间戳、更新版本或变动警报负载，生成的 `sourceRevision` 均必然更新；重复抓取相同双模式快照则保持 `sourceRevision` 严格不变。

## 6. 仍阻断的门槛与后续集成建议

1. **凭据注入门槛（Secret Manager）**：
   - 官方 API 网关必须携带 `KeyID` 请求头；
   - 生产部署时需由项目管理员将官方申请的 API Key 存入 GCP Secret Manager（名称对应 `source.json` 中的 `transport_victoria_key_id`），并通过环境变量 `TRANSPORT_VICTORIA_KEY_ID` 挂载。在凭据注入前，连接器维持 `auth_failed` 失败关闭。
2. **交通模式覆盖与前端/分析免责门槛**：
   - Transport Victoria 官方未提供公交车（Bus）与区域火车（V/Line）的 Service Alerts；
   - 下游聚合层（US4 视图及 UI 展示）必须保留覆盖声明，严禁在无警报时向用户展示“公交全线畅通无故障”的结论。
3. **静态 GTFS 联合定位门槛**：
   - GTFS-R 警报本身只包含 `route_id`、`stop_id`、`trip_id`，不含 WGS84 经纬度；
   - 警报地理化完全依赖与 T062 `victoria.transport.gtfs_static` 的关联匹配。若静态数据未命中或静态版本不一致，警报坐标必须保持 `geometry_geojson: null`，不得虚构经纬度。
4. **准入状态维持**：
   - 维持 `license_status = review_required` 与 `access_status = candidate`，不直接上线至定时调度器。
