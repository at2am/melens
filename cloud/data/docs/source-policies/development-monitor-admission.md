# City of Melbourne Development Activity Monitor: development admission

Reviewed 2026-09-30 Melbourne time. The [official dataset page](https://data.melbourne.vic.gov.au/explore/dataset/development-activity-monitor/) describes major commercial and residential development projects in the municipality. Its [official API metadata](https://data.melbourne.vic.gov.au/api/explore/v2.1/catalog/datasets/development-activity-monitor) declares CC BY with the [CC BY 4.0 licence](https://creativecommons.org/licenses/by/4.0/legalcode), identifies City of Melbourne as the provider, and describes a monthly update frequency. Product display must credit City of Melbourne, link to the dataset and licence, and identify Melens' point and status transformations.

On 2026-09-30 the metadata reported `data_processed = 2026-09-24T05:11:36Z` and 1,450 records. A live read-only connector run fetched all 1,450 records in 15 pages, with no rejections and 1,450 WGS84 project points. The API advertised a 10,000-request daily rate limit; the 100-request daily value in the manifest is a conservative **Melens operational cap**, not a provider guarantee. No third-party credential is needed. Raw response bodies are not retained, and temporary BigQuery load files have a one-day expiry with independent hourly orphan cleanup.

The record endpoint sends no `Last-Modified` header. The connector now reads the official `data_processed` metadata before and after pagination and fails closed if it changes. That timestamp is a **dataset snapshot version**, not a precise observation time for each project. Records with only `year_completed` retain a null `observed_at` and the annual completion year in source detail. Planned, approved, under-construction and completed source states remain distinguishable in the published title and summary; unknown upstream status never becomes approved. A `clue_block` value is retained in the connector's project payload, but no current CLUE polygon reference is asserted because the source gives no boundary vintage.

This admission is for a first development snapshot. Recurring publication remains disabled pending shared schedule and identity gates. The initial `coverage_from` in the source manifest is the first verified current snapshot, not a claimed project start date.

On 2026-09-30 the deployed `v_geo_records_current` gained complete-snapshot membership for this source. Only records present in the newest published upstream dataset version appear as current; removed projects remain in history without a fabricated cancellation status. A newer complete empty snapshot clears this source's current records. Failed snapshots and older versions published later cannot replace the current snapshot. The opt-in `test/integration/development-snapshot-view.test.ts` executed the deployed view logic in BigQuery and passed replacement, empty snapshot, failed future snapshot, old backfill, and resolved-state cases. The refreshed production planning view retained its 326 current projects. This validates snapshot visibility rules; it does not prove monthly collection.

The snapshot was published to the `melens-510012` development datasets as batch `batch_5fc8b7acca64218b77325f09d32be6739db3d21f` (1,450 inputs, 1,450 outputs, zero rejected). Repeating the same snapshot returned the same batch ID. BigQuery holds 1,450 source facts with `verified_open` rights. `v_geo_records_history` and `v_change_timeline` each show 59 active, 267 planned and 1,124 resolved project points, with no null geometry or dataset version. `v_planning_changes_current` intentionally shows only the 326 still active or planned projects; completed projects remain available in history. No exposed project carries an unversioned `com_block:` area reference. `v_source_coverage` reads `active` / `verified_open` / `current`, and the staging bucket had no remaining objects after publication. This verifies a one-shot development batch, not monthly scheduled collection.
